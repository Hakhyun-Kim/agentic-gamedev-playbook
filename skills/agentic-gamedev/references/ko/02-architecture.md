## 2. 아키텍처 4대 규약 (새 프로젝트 시작 시 복사해 쓸 것)

새 게임 프로젝트를 시작할 때 아래 4가지 규약을 **첫 커밋부터** 준수하면, 이후 밸런싱과 자동화 작업이 매우 수월해집니다.

### 2.1 순수 로직과 렌더링 분리 ★ (가장 중요)

게임 규칙(전투·경제·웨이브)은 **DOM이나 3D 렌더러를 전혀 몰라도 작동하는 순수 함수**로 작성합니다. 렌더러와 사운드는 이 로직이 반환하는 이벤트 배열을 받아 시각/청각 효과로 보여주기만 합니다.

```
data.(js|ts)     — 모든 밸런스 수치 (수치 튜닝은 여기서만 진행)
engine.(js|ts)   — 순수 로직: tick(state, dt) → events[] (봇과 실제 게임이 공유)
render.(js|ts)   — 렌더러: state를 화면에 그리고 events를 이펙트로 변환
sfx / music      — events를 오디오로 변환
main / app       — 위 요소들을 연결하는 메인 컨트롤러
```

이 구조 덕분에 **밸런스 봇을 쉽게 돌릴 수 있습니다.** 렌더링 단계(`render`)를 빼고 순수 엔진(`engine`)만 초고속으로 반복 호출하면 되니까요.

### 2.2 시드 결정론 (Seeded Determinism)

모든 난수 생성은 시드 기반 RNG(`mulberry32` 약 11줄)로 통일합니다. "동일한 시드 = 동일한 게임 전개"가 보장되면, 버그 재현과 밸런스 회귀 검증이 매우 직관적이게 됩니다.

```js
function mulberry32(seed) {
  return function () {
    seed |= 0; seed = (seed + 0x6D2B79F5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
```

엔진은 `createGame({ rng })` 형태로 RNG 함수를 전달받습니다. 실제 게임은 `Math.random`을 넘기고, 밸런스 봇은 `mulberry32(seed)`를 주입해서 시뮬레이션을 수행합니다.

**절차 생성 맵에 새 지형을 추가할 때 주의할 점 (실무 경험):**

1. **분기 판정 난수를 메인 스트림에서 뽑지 말 것:** "이 맵이 특수 지형인가?"를 일반 `rand()`로 추출하면, 그 뒤의 모든 난수 순서가 한 칸씩 밀려서 기존 맵들의 지형까지 엉뚱하게 바뀌어 버립니다. 특수 분기 난수는 시드 기반 파생 스트림으로 따로 돌려야 합니다.
2. **신규 구조물의 난수 추출은 반드시 기존 순서 뒤로 배치:** 중간에 난수 호출을 끼워 넣으면 1번과 마찬가지로 난수 스트림 밀림이 발생합니다.
3. **공용 배치 로직과의 가정을 유지할 것:** 몬스터 스폰 로직이 "방 내부는 평평한 바닥"을 전제로 한다면, 새 지형에서도 열린 사각형 영역만 방으로 지정해야 배치 로직 변경 없이 안전하게 동작합니다.
4. **길찾기 알고리즘과 지형 연결성 정의 맞추기:** BFS 길찾기가 4방향 기준이라면, 지형 연결성 판정도 4방향 기준으로 검사해야 합니다. 대각선으로만 연결된 통로는 그리드상 길로 보여도 봇이 통과하지 못해 영원히 갇히는 현상이 발생합니다.
5. **맵 면적이 달라지면 적 밀도 보정:** 지형 면적이 1.65배 넓어지면 동일한 수의 적이 흩어져 난이도가 의도치 않게 낮아집니다. 면적당 위협 수치를 맞춰야 전후 밸런스 비교가 의미를 갖습니다.

> **생성기 자동 검사 스크립트 작성 팁:**
> 브라우저 렌더링 없이 순수 지형 생성 함수만 호출해서, 수백 개 맵의 도달 가능성·고립 영역·벽 내부 배치 여부를 1초 만에 검사하는 CLI 스크립트(`npm run floor-check`)를 만들어 두면 좋습니다. 지형 로직을 고칠 때 커밋 전에 오류를 미리 잡을 수 있습니다.

### 2.2.1 온체인 및 확률형 게임에서의 결정론 응용

결정론은 원래 봇 검증용으로 설계했지만, 플레이어 신뢰 구축에도 유용합니다. "확률표를 보여주겠다"는 선언보다 **"동일한 시드와 선택으로 당신이 직접 결과를 재현해보라"**고 검증 기능을 제공하는 것이 훨씬 명확하거든요.

```js
// 온체인 트랜잭션 입력값(선택)과 주차 시드(블록 해시)만으로
// 게임 서버 없이 결과를 재현하여 온체인 이벤트와 대조
const replayed = resolveRun(seed, choices);
assert(replayed.floor === onchainEvent.floor);
```

> **기와장터 사례:**
> 던전 진행 판정을 순수 함수 모듈로 구성해두니 `scripts/verify-run.mjs` 스크립트로 결과 트랜잭션을 바이트 단위로 정확히 재현할 수 있었습니다. 게임 화면에도 "🔒 이 결과 검증하기" 버튼을 붙여 사용자가 시드 기반 결과를 온체인 기록과 직접 대조해 볼 수 있게 했습니다.
> 
> *참고: 실시간 요소(`block.timestamp`)가 개입하는 보스전 등은 아카이브 노드 없이 재현하기 어려워 검증 범위에서 제외하고, 이 제한사항도 문서에 명시했습니다.*

### 2.3 밸런스 단일 파일

모든 밸런스 수치(비용, 체력, 스케일링 공식, 드랍 확률)를 `data` 파일 하나에 모아 둡니다. 튜닝 포인트를 일원화하면, 봇과 실게임이 **동일한 수치 파일**을 읽게 되어 "봇 테스트는 통과했는데 실게임에서는 밸런스가 터지는" 현상을 방지할 수 있습니다.

### 2.4 이벤트 방출 구조

`tick()` 메서드는 내부 상태만 변경하고 **해당 프레임에 일어난 사건 목록(이벤트 배열)**을 반환합니다. 렌더러와 사운드 모듈은 이 이벤트를 수신해서 시각 이펙트와 효과음을 출력합니다.

```js
const events = tick(state, dt);   // [{type:'kill', x, y, gold}, {type:'castleHit', dmg}, ...]
renderer.onEvents(state, events); // 시각 효과 연출
handleEvents(events);             // 오디오 및 UI 알림 처리
```

이런 구조라면 밸런스 봇은 이벤트를 그냥 무시하고 넘어가고, 게임 렌더러는 화려한 연출을 입히게 됩니다. **단일 엔진, 두 소비자의 관계**가 성립하죠.

### 2.5 서로 다른 언어 간 수치 대조 — "어긋나면 테스트가 깨지게" 묶기

밸런스 단일 파일 원칙은 한 단일 런타임 내에서만 온전히 작동합니다. 게임 규칙 일부가 스마트 컨트랙트(Solidity)나 서버(TypeScript/C#)에 분산되어 있다면, 파일 하나로 합치기가 힘들죠.

이럴 때는 소스 코드를 직접 파싱해서 수치가 일치하는지 정규식 대조 검사를 작성하는 방법이 유용합니다. 해당 런타임을 실제로 실행하지 않고도 정적 대조가 가능하거든요.

```js
// 스마트 컨트랙트, 서버, 클라이언트의 확률 경계값을 파싱해서 비교
const table = {
  컨트랙트: doorThresholds('contracts/Guilds.sol', 'function doorRoll'),
  서버:     doorThresholds('server/src/guilds.ts', 'doorOutcome('),
  클라이언트: doorThresholds('client/src/chain/guilds.ts', 'function doorRollLocal'),
};
// 셋 중 하나라도 수치가 다르면 테스트 실패
```

이 방식은 TypeScript 빌드 파이프라인 전체를 불러오기 부담스러울 때, Node 테스트 환경에서 정규식으로 불변식을 대조할 때도 똑같이 유용하게 쓰입니다.

### 2.6 세션 저장 (localStorage) 안심 설계

자동 저장을 구현할 때는 ①저장 타이밍, ②쓰기 시점, ③불러오기 데이터 검증의 3가지를 명확히 분리해야 합니다.

1. **저장 시점:** 전투 진행 중이 아닌, 웨이브가 끝난 **안전한 준비 단계**에서만 스냅샷을 찍습니다. 시뮬레이션 중간 상태는 직렬화할 때 참조가 깨지거나 꼼수 저장이 발생하기 쉽습니다.
2. **비동기 안전 쓰기:** 직렬화는 상태 변경 즉시 수행하되, 실제 저장소 쓰기는 `requestIdleCallback`으로 미룹니다. 단, 탭이 숨겨지거나 닫히는 이벤트(`pagehide`, `visibilitychange`) 시에는 즉시 저장소를 비동기 없이 flush해야 데이터 유실을 막을 수 있습니다.
3. **불러오기 데이터 검증:** 사용자가 저장 파일을 수정했더라도 게임이 크래시되지 않도록 클램핑(Clamp) 처리를 해줍니다. 존재하지 않는 ID나 오버플로 수치는 안전한 범위로 자동 조정하거나 벤치로 대피시킵니다.
4. **양방향 회귀 테스트:** 정상적인 데이터 수신 검사 외에도, 의도적으로 유효하지 않은 수치를 넣은 저장 파일을 읽어와도 크래시 없이 안전한 상태로 복원되는지 검증 테스트를 작성합니다.

### 2.7 절차 생성 콘텐츠의 런타임 사양 신고

절차적으로 생성되는 문장이나 문제(예: 수학 퀴즈)가 살아있는 게임 상태(몬스터 체력, 남은 골드 등)를 참조하면, 몬스터 체력이 수만 단위로 치솟을 때 저학년에게 부적절한 나눗셈 문제가 나가는 식의 버그가 생깁니다.

이럴 때는 생성기가 결과를 뱉을 때 **어떤 조건과 제약사항을 검증해야 하는지 메타데이터(`needs`, `calc`)를 함께 반환**하도록 구현합니다.

```js
return {
  text: `오크 ${n}마리를 놓치면 성이 입는 피해는?`,
  answer: hp * n,
  needs: [hp, n],         // 해당 숫자들이 지문에 실제로 노출되어야 함
  calc: { mul: [hp, n] }, // 연산 종류와 피연산자 전달
};
```

생성기가 출력한 결과물이 해당 학년의 연산 범위(`fitsGrade`)를 벗어나면 자동으로 재추첨을 돌리고, 계속 실패할 경우 가장 안전한 기본 문제 유형으로 폴백하도록 만듭니다.

### 2.8 코드 분할 시 인터페이스 유지

프로젝트가 커져 단일 로직 파일이 2,000줄 넘게 부풀어 오르면 `engine/` 폴더 내 여러 모듈로 분할하되, **호출하는 쪽의 import 경로(`engine.js` 배럴 파일)는 변경하지 않고 유지**하는 것이 좋습니다.

```js
// engine.js — 내부 모듈들을 재수출(Re-export)하는 배럴 역할을 수행
export * from './engine/state.js';
export * from './engine/combat.js';

// 사용하는 곳: import { tick } from './engine.js' (경로 변경 없음)
```

호출부를 건드리지 않고 파일 분깃만 진행하면, 리팩토링 커밋의 diff가 순수 "코드 이동"으로만 구성되어 리뷰와 검증(기존 밸런스 봇 실행 결과 비교)이 매우 깔끔해집니다.
