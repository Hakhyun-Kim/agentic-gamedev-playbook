# Agentic GameDev Playbook — AI가 만들고 AI가 검증하는 게임 개발 방법론

> 서로 다른 장르와 프레임워크의 게임 4개에서 반복 검증한 "AI 페어 게임 개발" 방식을 정리했습니다. 새 게임을 시작할 때 이 플레이북을 기본 지침으로 활용하면 됩니다.

## 검증된 프로젝트

| 프로젝트 | 장르 | 스택 | 저장소 |
|----------|------|------|--------|
| **백층 던전** (dungeon100) | 3D 로그라이크 던전 크롤러 | React + Three.js + TypeScript + Vite | [dungeon100](https://github.com/Hakhyun-Kim/dungeon100) |
| **용사 수학 디펜스** (defenehero) | 3D 타워 디펜스 (교육) | Vanilla JS + Three.js + esbuild | [defenehero](https://github.com/Hakhyun-Kim/defenehero) |
| **두 문 러너** (door-runner) | 2D 러너 | Vanilla JS + Canvas | [door-runner](https://github.com/Hakhyun-Kim/door-runner) |
| **기와장터** (giwa-village) | 3D 멀티플레이 소셜 (온체인) | React Three Fiber + viem + Solidity | [giwa-village](https://github.com/Hakhyun-Kim/giwa-village) |

장르와 프레임워크는 모두 달랐지만 아래 제시하는 방법론은 4개 프로젝트 전체에 그대로 적용했습니다. 우연히 성공한 한두 개 사례가 아니라 다음 게임에도 그대로 복사해 쓸 수 있는 공통 틀입니다.

네 번째 프로젝트인 '기와장터'는 이전 프로젝트들과 형태가 조금 달랐습니다. 싱글플레이 런 개념이 없다 보니 밸런스 봇으로 사망 분포를 수집할 수 없었고, 핵심 규칙 일부는 Solidity로 스마트 컨트랙트에서 움직였거든요.

"그럼 밸런스 봇을 못 쓰는 건가?" 고민하다가 나온 결과가 2.5(소스 대조), 3.7(결정점 기대값), 3.8(시계 주입) 기법입니다. 방법론이 특정 프로젝트에 딱 안 맞는다고 곧바로 버리기보다는, 그 자리를 대체할 더 가벼운 검증 방식을 먼저 찾아보는 편이 훨씬 효과적이더라고요.

## 0. 한 줄 요약

> **복잡성을 외부 에셋이 아니라 코드 안에 두면, AI가 기획부터 구현·밸런싱·검증·배포까지 전 과정을 직접 돌릴 수 있습니다.**

이미지나 사운드 파일을 외부에서 가져오거나 생성 AI 이미지로 채우는 대신, **그래픽은 절차 생성 지오메트리로, 사운드는 Web Audio 합성 코드**로 직접 만들었습니다. 이렇게 하면 모든 산출물이 AI가 직접 읽고 수정할 수 있는 코드 텍스트로 남습니다. 사람은 재미의 방향만 잡고, 구현과 플레이 검증은 AI가 알아서 진행하게 되는 거죠.

이 검증 루프는 출시 후에도 계속 돌릴 수 있습니다. 동일한 밸런스 봇을 야간 스케줄에 걸어 두면 nightly 회귀를 자동으로 잡고, 매일 아침 트렌드를 스카우트해 다음 작업을 제안해 줍니다 (→ [11. 상시 자동화](#11-상시-자동화--사람이-자는-동안-도는-루프)).
